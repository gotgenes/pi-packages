## Keystones

One, not three.

### K1 — #639: the permission policy model (ADR 0009)

Direct dependants: #603, #604, #609, #680, #687, #691, #706, #720, #742, and PRs #692, #675, #684, #671, #638.
Adjacent claimants: #472, #698, #620.
Candidate answer for its enforcement seam: #686.

The last two runs recorded this as a configuration-shape decision, which under-reads it.
Its own body scopes it to capabilities and effects:

> whether and how access capabilities (reading vs. writing paths, exec, net) become first-class in policy

It also already states the substrate position, so the enforceability question does not need a separate decision:

> We are never going to beat an agent sandbox at containment.
> What we can be is the best at routing human attention to consequential actions — and consequence is about effects (read vs. write vs. exec vs. net), not command spellings.

<!-- -->

> State the threat model explicitly: a cooperative-but-fallible agent; attention routing, not containment; a future sandbox as the enforcement seam.

Issue #686 proposes one concrete sandbox (`nono`) for that seam.
It therefore belongs inside K1's option space rather than beside it — and, unlike a standalone stance, it does not need the reporter's pending answer before K1 can proceed.

The ordering K1 implies is enforceability first, then capabilities, then configuration.
Configuration that promises what the substrate cannot deliver creates false assurance, which is the same reasoning the charter applies to log redaction.
Two open items are already configuration *about* a workaround: #680 asks to configure indirection-wrapper flooring, and #706 asks to inspect wrapped commands instead of always asking.
Both exist because the parser cannot read those commands, and both may dissolve rather than need answering if the substrate changes.

The cost of the delay is measurable.
Issue #639 has had zero activity since 2026-07-23.
In that month #671 and #684 went from green and `CLEAN` to `CONFLICTING`, and the five parked PRs have collectively been waiting an average of 25 days.

## Findings that changed a rank

- **#785 duplicated #609, and was ranked separately by mistake.**
  It reported that a redirect destination is gated by the same direction-agnostic surface as a read.
  Issue #609 reported the same mechanism a month earlier: *"Bash matching intentionally removes the redirect from the command, while the path gate does not distinguish reads from writes."*
  An earlier draft of this document ranked #785 at 1 and #609 at 22, as separate items.
  Closed as a duplicate with credit; the two elements unique to it — the bare non-existent destination (`> newfile`) and the concrete `redirect`-surface proposal — are recorded as input to K1.

- **#742 is verified on `main`, by its own documentation.**
  The deferral from #306 is intact, so `if true; then rm y; fi` is matched as one string and an explicit `rm *` deny rule does not fire.

- **Nothing in the bash pipeline carries access direction.**
  The only direction-aware structure in the access-intent layer is `READ_ONLY_PATH_BEARING_TOOLS` (`path-surfaces.ts:5`), which lists built-in tool names (`read`, `find`, `grep`, `ls`) and exists to gate the Pi infrastructure auto-allow.
  This is the general gap #639 was filed to decide, not a defect to patch.

- **#465 was reclassified by a live test, and dropped from an umbrella to a one-line defect.**
  It was deferred three consecutive runs as "needs decomposition."
  Running the round trip showed the capability already exists — a child's result can be a question, and `resume(id, prompt)` answers it with prior context intact.
  What is missing is the handle: `buildDetails` sets `agentId` into `details` (`src/tools/helpers.ts:44`), which is renderer metadata, while the model receives only `content[].text`.
  The background path puts the ID in that text (`src/tools/background-spawner.ts:52`) and repeats it in the completion notification; the foreground path does neither (`src/tools/foreground-runner.ts:126-130`).
  Filed as #798; #465 stays open until it lands.

- **A third-party extension was probably broken by v27.0.0, and nobody had told its author.**
  TacoTakumi commented on #472 on 2026-08-21 — the day v27.0.0 shipped — describing `pi-permission-classifier`, an allow-capable chain link that "follows the pi-permission-model-judge pattern."
  That release's breaking change re-emits `permissions:ready` at each node's first `before_agent_start`, so *"a consumer that registers unconditionally on every emission hits a duplicate-registration throw on every session."*
  A heads-up was posted naming the ready-cadence change, the session-keyed locator, the ADR 0012 registration channel, and model-judge 2.0.0 as the reference migration.

- **#735 was very likely fixed before anyone read it.**
  It was filed 2026-08-14 against 20.10.0, reporting the hardcoded ten-minute timeout on a dead or non-draining parent. #721's heartbeat liveness shipped in v26.2.0 on 2026-08-17, and a child now abandons in seconds when no heartbeat is published — which covers both reported scenarios.

- **Ten of seventeen open PRs are now `CONFLICTING/DIRTY`, up from four.**
  #671, #684, #693 and #703 were all green and `CLEAN` at the last triage and are conflicting now.
  This is not contributor neglect — it is the pace of Phase 13 and ADR 0012 landing in the same files.
  It compounds while K1 stays undecided.

- **The two clean PRs are genuinely clean, and their greens are not stale.**
  #747 and #748 are `MERGEABLE/CLEAN` with passing checks from 2026-08-15.
  `service-adapter.ts` last changed 2026-07-14, `service.ts` 2026-07-22, and `index.ts` 2026-08-13 — all before those runs.

- **#757's green would have been stale even if it were green.**

  It fails the Fallow audit regardless.
