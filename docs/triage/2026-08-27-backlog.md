## Findings that changed a rank

- **Issue #821 is real, and the drop happens later in the pipeline than the report supposed.**
  The AST walker collects the token correctly; it dies in classification.
  `REGEX_METACHAR_PATTERN` at `packages/pi-permission-system/src/access-intent/bash/token-classification.ts:145` includes a `\[.*?\]` alternation to reject grep regex arguments, and it discards any path token containing a shell bracket glob, in every command:

  ```text
  /etc/[p]asswd  => null                 # dropped before any surface sees it
  /et[c]/pa*     => null
  /etc/pa?sword  => "/etc/pa?sword"      # collected correctly
  /etc/pa*sword  => "/etc/pa*sword"
  ~/.ssh/id_[r]sa => null
  ```

  So `cat /etc/[p]asswd` executes with no prompt on 27.1.0.
  ADR 0013 §10 already states the answer — an unresolvable token consults both directional surfaces — so this is a §10 violation with a settled remedy, not a model question.

- **Issue #815 is worse than reported, and the reporter could not have known.**
  Their root cause is correct: `getToolPermission` at `packages/pi-permission-system/src/permission-manager.ts:263` evaluates the surface against the literal pattern `"*"`, so a `deny` catch-all strips the tool before any nested rule can be reached.
  What verification added is that `docs/configuration.md` ships that exact shape twice, and both recipes are dead:

  ```text
  #815 bash tool exposure     => deny    # "git *": "ask" unreachable
  docs Restricted-Bash recipe => deny    # docs/configuration.md:987
  docs write recipe           => deny    # docs/configuration.md:316
  ```

  A user adopting the documented deny-by-default posture loses the tool entirely, sees no error, and the model never learns the tool existed.
  That is a documentation-correctness defect as much as a code one, and it is why this outranks everything except the fail-open.

- **Issue #800 was delivered while it sat in the queue.**
  It asks for read-only bash commands to bypass the `external_directory` gate.
  Release 27.1.0 shipped `external_directory_read` as a directional surface (#807) and stopped flooring wrappers that run a proven pure reader (#803), five days after the issue was filed.
  The remaining question is whether `external_directory_read: {"*": "allow"}` plus the pure-reader core covers the reporter's actual cases, which is a reply rather than a work item.

- **PR #811 is the cleanest thing in the tracker and its green is fresh.**
  Twelve lines, one file, `MERGEABLE/CLEAN`, checks passing from today.
  `packages/pi-subagents/src/index.ts` last changed 2026-08-13, well before the run.
