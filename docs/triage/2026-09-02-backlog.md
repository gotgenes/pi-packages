## Findings that changed a rank

- **Issue #815 was verified broken, then fixed and released while this document was being written — and this run published the stale reading.**
  At 06:16Z the defect reproduced exactly as filed, by constructing a `PermissionManager` over an in-memory policy loader and probing `getToolPermission`:

  ```text
  reporter's config  {"*":"deny","git *":"ask"}          => deny   # tool stripped
  docs Restricted-Bash recipe  configuration.md:985      => deny   # documented recipe dead
  docs write recipe            configuration.md:316      => deny   # documented recipe dead
  bare string  "bash": "deny"                            => deny   # intended
  ```

  Commit `ce46b6c7` landed at 07:02Z — 46 minutes later — and shipped in 30.1.0; the issue closed at 15:32Z.
  The measurement was never re-run before the table was published, which is precisely the rule this repo already writes down: a measurement is scoped to the commit it was taken at, and must be re-run after any behavior change rather than defended.

  Re-running it also required **re-aiming** it, which is the sharper half of the lesson.
  The fix did not change `getToolPermission`; it added `isToolFullyDenied` and moved the exposure decision onto it, so the original probe still reports `deny` on current `main` and would have "confirmed" a defect that no longer exists:

  ```text
  getToolPermission("bash")  => deny      # unchanged, and no longer the exposure decision
  shouldExposeTool via isToolFullyDenied:
    reporter's config          => EXPOSED
    docs Restricted-Bash       => EXPOSED
    docs write recipe          => EXPOSED
    bare "bash": "deny"        => hidden   # intended behavior preserved
  ```

  A re-run that keeps pointing at the old symbol is not a re-run.
  Both the subject and the timestamp have to be re-derived.

- **Issue #839 is the uncollected half of a gap Phase 14 already closed once.**
  Step 4 (#742) made command *enumeration* descend control-flow node types.
  Token *collection* was not changed, and it still reads text from two node types only:

  ```text
  token-collection.ts:47   if (node.type === "command")       return collectCommandTokens(node);
  token-collection.ts:48   if (node.type === "file_redirect") return collectRedirectTokens(node);
  ```

  A `for_statement` operand word is a direct child of the statement node, so `for f in /outside/*` names a path that reaches neither `path` nor `external_directory`.
  That is a gate that never fires, which is why it outranks the silent-wrong-result at rank 2.

- **The roadmap has moved the false-asks closer than it looks, and the operator asked exactly the right question.**
  The classifier is deliberately three-valued — definitely-path by shape, definitely-not by prelude, and unknown — and only the *unknown* bucket is resolved against the filesystem by the #645 existence probe.
  In `bash-path-resolver.ts:451` the probe is the **else** branch:

  ```text
  const candidate = classifyTokenAsPathCandidate(token);
  if (!candidate) { … probeBareToken(token, base) … continue; }   // precision lives here
  … collectIfExternal(…)                                          // shape-accepted: never probed
  ```

  Both false-asks are shape-accepted tokens that bypass the probe: #859's `cc83d7b48..origin/master` via the `token.includes("..")` branch (line 65), and #863's inline script via the leading-`/` branch.
  The probe cannot simply be extended to shape-accepted tokens, because a *write* destination legitimately does not exist yet, so nonexistence would become a fail-open.
  That is what Phase 14 changed: `projectExternalPaths` now iterates `{ token, base, effect }`, so the per-token effect Step 2 (#807) introduced is already threaded into the exact loop where the decision would be made.
  Nonexistence is admissible evidence *for a proven read* and not for a write — a distinction the code could not express before the direction axis shipped.
  The mechanism is in place; nobody has spent the step.

  There are two independent levers, and they cover different members of the family:

  1. **Tighten the shape branches.**
     Requires no effect and no probe — `..` should have to be a path *component*, not a substring.
     This closes #859 outright, and is what its reporter's patch does.
  2. **Extend the existence probe to shape-accepted tokens, gated on a proven read.**
     This is the one that needs the direction axis, and it is what #863 and the case below require.

- **This triage session generated a fourth instance of the false-ask class, twice, while writing this document.**
  The command used to prove the charters were unchanged (Carried forward, above) passes `git log` a `-L` range argument:

  ```text
  git log -L '/^## Scope and non-goals/,/^## Documentation/:packages/pi-permission-system/README.md'
  ```

  After quote removal that token starts with `/`, so the leading-`/` branch accepts it.
  Probing the shipped classifier directly:

  ```text
  /^## Scope and non-goals/,/^## Documentation/: => PATH CANDIDATE
  cc83d7b48..origin/master                       => PATH CANDIDATE
  // check which packages are installedconst fs  => PATH CANDIDATE
  /etc/passwd                                    => PATH CANDIDATE
  ```

  It is indistinguishable from `/etc/passwd` to the gate, and it resolves to a nonexistent absolute directory named after a regex.
  The wrinkle worth keeping: a `-L` argument is `<range>:<file>`, so the token *ends* in a real repository path while not being a path itself — token-level classification cannot get this right by tightening shapes alone.

  All three concrete cases now on record — #859, #863, and this one — are arguments to **read-only `git` or `node` invocations** whose syntax collides with path shape.
  That sharpens lever 2's limitation: `git` is deliberately *not* in the pure-reader core (`git checkout` writes), and ADR 0013 §7 declines to maintain the long tail, so `git log`'s read-ness is provable only once a user declares it in `commandEffects`.
  Absent that declaration the effect is unknown, the token fails closed, and the probe stays inadmissible.
  Whether a shipped `commandEffects` default for a few high-traffic subcommands is consistent with §7's refusal is a genuine design question, not a detail — it should be asked in Phase 15's planning rather than settled here.
